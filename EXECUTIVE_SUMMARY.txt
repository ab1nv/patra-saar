--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

PatraSaar is a retrieval-augmented question-answering tool for Indian statutory
law. It answers questions about ten indexed sources - the Indian Penal Code,
Bharatiya Nyaya Sanhita, Bharatiya Sakshya Adhiniyam, Bharatiya Nagarik Suraksha
Sanhita, Code of Criminal Procedure, Code of Civil Procedure, the Constitution of
India, the Indian Contract Act, the IT Act, and the Companies Act - using ONLY an
indexed corpus of about 3,270 parsed sections. A language model is constrained to
answer from the retrieved sections and must express every legal assertion as a
machine-checkable citation containing a verbatim quote. A deterministic, NON-LLM
verifier then checks every citation before it is shown: does the section exist,
was it retrieved for this question, and does the quote appear character-for-
character in the source text. Verified citations are shown as such and can be
expanded to reveal the real statutory text; failed citations are struck through
and labelled with the exact reason. If retrieval finds nothing above threshold,
the system refuses to answer rather than guessing.

The thesis is not that hallucination can be prevented, but that it can be caught
deterministically and measured. To prove it, the project ships a HALLUCINATION
AUDIT: the same model, on the same 30-question ground-truth set, with and without
retrieval-plus-verification, scored automatically against the corpus.

Tagline: "It cites the law, or it says it doesn't know."

Why now: on 2 July 2026 the Supreme Court of India, in Pooja Ramesh Singh v.
Jammu & Kashmir Bank Ltd. (2026 INSC 668), set aside tribunal orders that relied
on AI-hallucinated precedents. That is precisely the failure mode this project
targets.

2. FEATURE SUMMARY
--------------------------------------------------------------------------------

VERIFIED CITATIONS (core)
  - Grammar: [[ACT_CODE s.NUMBER | "verbatim quote"]].
  - Three server-side checks: sectionExists, wasRetrieved, quoteVerbatim.
  - Verified chips open a drawer with the real statutory text; failures show the
    exact reason (section_not_found / not_retrieved / quote_not_verbatim).
  - Sub-section syntax (e.g. BNS s.318(2)) normalised to the base section.

HALLUCINATION AUDIT (public, /audit)
  - 30 ground-truth questions: 24 in-corpus, 3 non-existent sections, 3 outside
    the indexed acts.
  - Two arms on the same model: Baseline (no retrieval) vs PatraSaar
    (retrieve -> constrain -> verify).
  - Deterministic scoring: exists / verbatim / correct / fabricated, per-question
    accuracy, fabricated-question rate.
  - Published methodology and explicit limitations.

  BENCHMARK DETAIL
  Model: qwen/qwen3.8-27b (Groq).  Sample: 30 questions (24 in-corpus).
  Run: 2026-09-15.  Raw data: data/audit-results.json.  Reproduce: pnpm audit:run.

  --------------------------------------------------------------------------
  A. WHAT IS COMPARED (MODELS AND ARMS)
  --------------------------------------------------------------------------
  Both arms use the SAME generator: qwen/qwen3.8-27b, served by Groq over the
  OpenAI-compatible chat-completions endpoint (model id from GROQ_MODEL),
  temperature 0.1, no fine-tuning and no retrieval-specific training.

  ARM 1 "Baseline" (ungrounded): the same model, given the same citation
    grammar but NO retrieved sections, answering from parametric memory.
    This stands in for "just ask a chatbot". It is NOT ChatGPT, Claude,
    Gemini or any commercial assistant - it is one open-weight model on a
    free tier, used as an apples-to-apples control for the effect of
    retrieval + verification. The /audit page states this explicitly.
  ARM 2 "PatraSaar" (grounded + verified): the same model constrained to the
    retrieved sections, with the output checked server-side by a
    deterministic verifier.

  Because both arms share the identical model and temperature, the measured
  difference is attributable to retrieval + verification, not to model choice.

  --------------------------------------------------------------------------
  B. METHODOLOGY (END TO END)
  --------------------------------------------------------------------------
  B1. QUESTION SET - data/audit-questions.json, 30 questions:
        * 24 in-corpus (q01-q24): each names a ground-truth section that was
          verified to exist in data/corpus.json before the run.
        * 3 non-existent section (q25-q27): IPC 991, BNS 700, CrPC 812.
        * 3 out-of-corpus (q28-q30): GST on textiles, Maharashtra Rent
          Control Act, SEBI insider-trading rules.
      Non-adversarial, drawn from the most commonly consulted provisions
      across all ten indexed sources.

  B2. RETRIEVAL (PatraSaar arm only):
        * In-process BM25 over the parsed corpus (k1 = 1.5, b = 0.75), with
          the section TITLE repeated x3 in the token stream, so titles weigh
          ~3x over body text.
        * Hybrid exact lookup: a section/article named in the question is
          pinned first with matchType "exact".
        * Named-act boost x1.8 when the question names an act.
        * Top-K = 8 candidates (exact pins merged with BM25 hits).
        * Abstention gate: no exact pin AND (best lexical score = 0 OR
          coverage < 0.34), where coverage is the share of the question's
          content terms present in the best section.
        * Content-term extraction removes stopwords, act-name vocabulary
          ("indian", "penal", "constitution", "crpc", ...) and query filler
          ("defined", "explain", ...) so they cannot dilute coverage.

  B3. PROMPTING:
        * Grounded system prompt contains ONLY the retrieved sections plus a
          fixed rule set: no outside knowledge, every assertion emitted as
          [[ACT_CODE s.NUMBER | "verbatim quote"]].
        * Context budget per request: <= 1,300 chars per section and
          <= 4,500 chars total (free-tier token safeguard). Quotes are still
          verified against the FULL section text server-side.
        * Baseline prompt uses the same citation grammar but instructs the
          model to answer from its own knowledge.

  B4. GENERATION PARAMETERS (identical both arms): temperature 0.1;
      max_tokens 300 (baseline) / 650 (PatraSaar); SDK retries disabled and a
      30s timeout so the harness owns retrying.

  B5. VERIFICATION (PatraSaar arm only) - three deterministic checks, in
      order, on the assembled answer:
        1. sectionExists - the cited act + number resolves in the corpus.
        2. wasRetrieved  - that section was in the retrieved set for THIS
                           question (the model cannot cite a real section it
                           was never shown).
        3. quoteVerbatim - the quoted string appears in the section text
                           after normalization (lowercase, unify quotes and
                           dashes, collapse whitespace, strip punctuation).
      The verifier is plain string-matching, NOT a second language model, so
      it cannot hallucinate about whether something was hallucinated.
      Failure reasons recorded: section_not_found / not_retrieved /
      quote_not_verbatim.

  B6. SCORING (src/lib/audit/score.ts), applied to BOTH arms, per citation:
        exists     = resolves to a real section in the corpus
        verbatim   = quote found in that section's text
        correct    = resolved id == the question's ground-truth section
        fabricated = does NOT resolve to any real section
        verified   = exists AND retrieved AND verbatim (grounded only)
      Per question:
        questionAccuracy       = share of in-corpus questions where at least
                                 one citation matched the ground-truth section
        fabricatedQuestionRate = share of questions containing >=1 citation
                                 that resolves to no real section
      The baseline is scored on exists/verbatim/correct only; "verified" and
      "retrieved" are undefined for it by construction (nothing was retrieved).

  B7. RUN MECHANICS: both arms run per question (in parallel), scored, and
      saved incrementally to data/audit-results.json with 1.5s pacing and
      retry-after-aware backoff (up to 8 tries). The run resumes from the last
      completed question after an interruption. Full run: ~20-30 min on the
      Groq free tier (token-per-minute bound).

  TABLE 3 - ERROR TAXONOMY OF THE BASELINE (59 citations over 30 questions)

        q30 (SEBI insider-trading rules)         -> cited it:3.

      classic "confidently cites a real but irrelevant provision" failure.

  --------------------------------------------------------------------------
  F. WHAT THE NUMBERS DO AND DO NOT PROVE
  --------------------------------------------------------------------------
  Prove: for THIS model, on THIS set, a deterministic verifier converts
  "citations we hope are right" into "citations checked against source text",
  and an ungrounded model's quotations are overwhelmingly NOT the statute even
  when its section numbers are correct.
  Do NOT prove: general legal correctness; behaviour of other models; that a
  correctly quoted section is legally applicable (verification is provenance,
  not reasoning); statistical significance (n=30, single model,
  non-adversarial, not peer-reviewed).

  --------------------------------------------------------------------------
  G. HOW IT IS ACHIEVED (MECHANISM)
  --------------------------------------------------------------------------
  1. Section-level corpus parsing preserves number/title/body, enabling both
     O(1) exact lookup and a faithful BM25 index. (Blind chunking could not
     support either.)
  2. Hybrid retrieval (exact pin + BM25 + act boost) puts the operative
     section in front of the model.
  3. A constrained prompt with a machine-checkable citation grammar converts
     prose assertions into verifiable records.
  4. A deterministic three-check verifier, independent of any LLM, gates what
     the user sees and records the failure reason when it blocks a citation.
  5. A coverage-gated abstention path replaces low-confidence answering.
  6. The audit reuses the SHIPPED verifier functions (checkSectionExists /
     checkQuoteVerbatim), so the benchmark measures the production system, not
     a side harness.

  --------------------------------------------------------------------------
  H. HOW IT IMPROVES ON STRONGER / FUTURE MODELS
  --------------------------------------------------------------------------
  The verifier is model-agnostic: only the generator call is swappable (one
  env var for the model id, plus a provider adapter for a non-Groq endpoint).
  A stronger generator - a frontier assistant such as the ones referred to as
  "Claude Fable" or "GPT Astra", or any future model - changes three things,
  none of which requires touching the verifier:

  H1. Fewer authoring errors. PatraSaar's 2/85 (2.4%) non-verbatim quotes are
      instruction-following failures. Stronger models copy "character-for-
      character" more reliably, pushing the verified rate from 97.6% toward
      100%. The baseline's verbatim rate would also rise, so the headline GAP
      may NARROW - which is the honest point: the value of the verifier is not
      a bigger gap, it is a GUARANTEE that holds regardless of model strength.
  H2. Better section selection. Stronger reasoning and longer context let the
      model use more retrieved candidates and pick the operative one, fixing
      the q10-style ranking miss. Top-K and the context budget can then be
      raised without truncation.
  H3. Fewer false refusals. q08/q09/q14 show the baseline refusing answerable
      questions; stronger models refuse less, and the grounded arm's
      abstention gate remains the safety net.

  What does NOT change with model strength:
    * Fabricated citations shown to the user stay at 0%, because the verifier
      blocks anything that does not resolve, was not retrieved, or is not a
      verbatim quote - whatever model wrote it.
    * Abstention correctness is governed by the retrieval gate, not the model.
  Architectural claim: verification quality is INDEPENDENT of generator
  capability; only the verified-YIELD improves with the model.

  NOTE ON NAMED MODELS: no figures are claimed here for "Claude Fable",
  "GPT Astra" or any model that was not actually run. Project convention - and
  the entire point of this product - is that a number must be measured before
  it is stated. To obtain such figures, add the model as a third arm and re-run.
  The harness already supports arbitrary arms; a multi-model run is a small
  adapter plus an API key.

  H4. PLANNED UPGRADES TO THE BENCHMARK ITSELF
      * Larger n and a per-act breakdown to expose retrieval weak spots (q10).
      * Multi-model matrix (add frontier baselines via OpenRouter).
      * Adversarial set: near-miss section numbers, repealed provisions,
        deliberate cross-act confusion.
      * Human rubric for legal applicability, with inter-rater agreement, to
        cover what provenance checks cannot.
      * Hybrid dense + BM25 retrieval with a cross-encoder re-ranker.
      * Report latency and cost per verified answer, not just accuracy.

  LIMITATIONS (stated on /audit)
  Small (30 questions), self-run, single-model, non-adversarial and not
  peer-reviewed. It measures citation provenance, not legal reasoning. It
  mirrors, at much smaller scale, the design of the Stanford RegLab audits of
  commercial legal-AI tools.

ABSTENTION
  - Coverage gate on retrieval: weak matches produce a refusal, not a guess.

CHAT WORKSPACE
  - Streaming markdown answers; inline citation chips; citation drawer with the
    verbatim section text.
  - Collapsible, drag-resizable sidebar (a drawer on mobile).
  - Pin, rename and delete chats; model-generated chat titles.
  - Incognito mode (nothing persisted).
  - File attachments (PDF/text) whose text is extracted and sent to the model.
  - Select any phrase in an answer to cross-question it with chat context.
  - Fully responsive with scroll-reveal and entrance animations.

CORPUS
  - Ten sources parsed at section/article level from the official PDFs.
  - Repealed/omitted sections excluded; per-act counts published.

AUTH AND PERSISTENCE
  - Single seeded user, scrypt-hashed password, HS256 JWT in an httpOnly cookie,
    actually verified in middleware.
  - Neon Postgres via Drizzle; in-memory fallback if the database is unreachable.

OFFLINE DEMO MODE
  - With no GROQ_API_KEY, deterministic extractive answers with real verbatim
    citations keep the app and tests working.

3. TECHNICAL SUMMARY
--------------------------------------------------------------------------------

STACK
  Next.js 16 (App Router, Node runtime) · TypeScript (strict) · Tailwind CSS v4 ·
  Groq API (qwen/qwen3.8-27b) · Neon Postgres + Drizzle ORM · in-process BM25 ·
  unpdf · jose + scrypt · Vitest · Playwright. Deployed on Vercel.

REQUEST LIFECYCLE (POST /api/chat)
  1. Validate session cookie and Zod body.
  2. Resolve or create the case (skipped in incognito mode).
  3. retrieve(): exact-section lookup + BM25 over title/body, with a coverage
     gate for abstention.
  4. Build a prompt containing only the retrieved sections and the citation
     rules.
  5. Stream tokens to the browser as typed SSE events (meta, token).
  6. Run verifyCitations() server-side on the assembled answer.
  7. Persist (unless incognito), generate a short title, emit citations, title,
     done.

KEY DESIGN DECISIONS
  - BM25, not a vector database. ~3,270 sections; brute-force BM25 is
    milliseconds, deterministic and unit-testable; legal queries are lexically
    precise.
  - Section-level parsing, not blind chunking. Preserving number/title/body is
    what makes exact lookup and citation verification possible.
  - A deterministic verifier, not a second LLM. The fact-checking literature
    shows LLM verifiers can themselves hallucinate.
  - Bounded prompt context to respect the free-tier token limit; quotes are still
    verified against the full section text.
  - One application, one language, one deploy target.

THE VERIFIER'S HONEST LIMIT
  It proves provenance, not legal reasoning: a section can be quoted correctly
  and still be applied to the wrong situation.

TESTS
  33 Vitest unit tests and Playwright E2E on desktop AND mobile viewports. CI
  runs typecheck, lint, knip, unit tests, a Postgres service container, seed,
  build and E2E - with no repository secrets required.

LIMITATIONS
  No case law, state amendments, rules or notifications; English only; single
  user; BM25 weak on purely conceptual paraphrase; the audit is small, self-run,
  single-model and non-adversarial.
